Just like we discussed for *Combination Sum*, creating a new array instance using the spread operator on every recursive step can be a memory bottleneck if the input array scales up.

To make your code use $O(N)$ auxiliary space instead of allocating multiple arrays, you can use explicit **Backtracking (Push & Pop)**:

```javascript
var subsets = function(nums) {
    const result = [];
    
    const fn = (index, currentPath) => {
        // Make a hard copy only when saving a valid subset state
        result.push([...currentPath]); 
        
        for (let i = index; i < nums.length; i++) {
            // 1. Action: Include nums[i]
            currentPath.push(nums[i]);
            
            // 2. Recursion: Explore further down the tree
            fn(i + 1, currentPath);
            
            // 3. Backtrack: Remove nums[i] to try the next branch
            currentPath.pop();
        }
    }
    
    fn(0, []);
    return result;
};

```

### ## The Quick Answer: LeetCode's Testing Bottleneck

The short answer is **Garbage Collection (GC)** and **Test Case Dataset Size**.

LeetCode 78 (Subsets) has very small constraints: `nums.length` is at most `10`.

* For an array of size 10, the total number of subsets is $2^{10} = 1024$.
* Generating 1,024 small arrays using the spread operator (`[...res]`) takes almost no time at all.

When a dataset is this tiny, the time difference between creating new arrays versus pushing/popping into a single array is microscopic (fractions of a millisecond). The variation you see on LeetCode between 0ms and 1ms is mostly **network jitter** or the LeetCode machine running your code slightly slower or faster during that specific split second. If you submit your backtracking code 3 more times, you'll likely hit 0ms on one of them!

---

### ## The Deeper Engineering Reason: Hidden Costs

Look closely at where your copy happens now:

```javascript
result.push([...res]) // Inside backtracking code

```

In your original code, you copied the array inside the loop *only* down the specific path you were visiting. In the Backtracking code, you are making a copy of `res` **every single time** `fn` is called, right at the top of the function.

Additionally, mutating a single array over and over (`push` and `pop`) forces the JavaScript engine to constantly look up and modify that shared reference in memory, whereas allocating small, localized immutable arrays via the spread operator can sometimes be optimized incredibly fast by V8's internal optimization profiling.
